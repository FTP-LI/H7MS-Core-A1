# H7MS OTA 可行性与推荐架构

2026-10-12 · 依据当前 H735VGH6 Direct SMPS 引脚/外围规划。以下为待实现的设计要求，不是已有功能声明。

## 可行性结论

现有主控、外部 NOR、USB 和上位机串口可以支撑应用 OTA，**无需仅因 OTA 更换 H735，也无需增加外部 RAM**。主要工作在 Bootloader、存储驱动、掉电状态机和测试，而不是新增接口。

| 当前资源 | 已核实的约束 | 对 OTA 的影响 |
| --- | --- | --- |
| H735 内部 Flash | 1 MiB；8 个 128 KiB 用户扇区；Flash word 为 32 B，另含 ECC | 分区按扇区边界；写入按 Flash word 规则设计，不能把标志位当普通可反复写的字节 |
| 单 Bank | 不具备双 Bank 交替执行/擦写的基础 | 安装进入维护模式；不承诺同时维持运动控制实时性 |
| RAM | 560 KiB 非备份 RAM，分布在多个存储域，另有 4 KiB 备份 RAM | 分块传输、分块校验/搬运，不把整份近 1 MiB 固件装入 RAM |
| W25Q128JVPIQ | 128 Mbit = 16 MiB；256 B 编程页，4 KiB 扇区，另支持 32/64 KiB 块擦除 | 可分配更新/恢复区；驱动处理页边界、忙状态、写保护和掉电恢复 |
| 网络 | 当前没有无线模块和以太网 PHY 基线 | 上位机提供网络，MCU 不必运行 TLS/IP 云客户端 |
| 电源 | Direct SMPS；USB 默认自供电，VBUS 检测用途 | 更新时保持外部供电；插 USB 不等于 MCU 已得到维护电源 |

器件依据：[ST DS13312 Rev 4 §3.3](https://www.st.com/resource/en/datasheet/stm32h735ig.pdf)、[ST H7 单 Bank 资源说明](https://www.st.com/resource/en/brochure/brstm32h7.pdf)、[本地 Winbond 原厂 Rev F 手册](../H7MS/技术依据/外围器件/W25Q128JV_RevF.pdf)。接口依据为项目[引脚规划](../H7MS/引脚规划.md)。安装期间按同 Bank 访问受擦写影响的保守条件设计；具体停顿、超时和 Flash 勘误需在驱动阶段按 RM0468、实物硅版本复核，本次未成功获取 RM0468 全文。

## 推荐链路与职责

```mermaid
flowchart LR
  RELEASE["签名完整固件包"] --> HOST["Linux 上位机\n网络下载 / 版本编排 / 记录"]
  HOST -->|"USB FS 或 UART8"| APP["H735 应用\n分块接收 / 维护请求"]
  APP --> NOR["W25Q128\n候选镜像 / 已知可用副本 / 状态"]
  NOR --> BOOT["独立 Bootloader\n验签 / 安装 / 恢复"]
  BOOT --> TRIAL["内部 Flash 应用\n试启动与自检"]
  TRIAL -->|"确认"| RUN["正常运行"]
  TRIAL -->|"失败或未确认复位"| BOOT
  HOST -.->|"应用失效时的维护通道"| BOOT
```

上位机负责网络、包下载、适配板型与版本检查、进度展示和发布日志。MCU 接收层负责有界缓冲、重传、NOR 写入和请求维护；Bootloader 独立负责镜像合法性、安装决策和恢复。即使上位机先验过签，MCU 仍须验签，不能只信任一条“校验通过”的命令。

Bootloader 在应用损坏时也要能独立初始化 NOR 和至少一种维护传输。首版建议先实现 **UART8 Boot 维护通道**，再评估 USB Boot 维护的体积和复杂度。若只在应用中实现更新协议，坏应用就可能使远程恢复失效；仅预留 SWD 解决的是现场恢复。

UART8 远程维护的前提是上位机与 UART8 实际连接。若成品只连接 USB，则 Bootloader 也必须提供 USB 维护，不能靠一个未接线的串口宣称具备远程救援。上位机还需能识别应用/Boot 两种通信状态并重新连接。

| 用途 | 复用资源 | 规划约束 |
| --- | --- | --- |
| 首选常规下发 | USB FS Device，PA11/PA12 | 实际为 USB_OTG_HS 控制器的内部 FS PHY，线路速率 12 Mbit/s；不是外部 PHY 的 480 Mbit/s |
| 备用下发/Boot 维护 | UART8，PE1 TX / PE0 RX | 独立于四组设备串口；约定维护帧，不把日志与未封装二进制混发 |
| 镜像存储 | OCTOSPIM1 Quad NOR | PB2/PB6/PD11/PB0/PE2/PA1，沿用已有规划；读写与日志调度需互斥 |
| 三路 CAN | 保持 FDCAN1/2/3 | 首版不占用电机总线传大固件；将来多节点 CAN 更新单独定义协议和停机调度 |
| 本地救援 | BOOT0、NRST、SWD | 保留当前接口；ROM Bootloader 支持的具体接口/管脚须另按 AN2606 核对，不能假定 UART8 就是 ROM 下载串口 |

上述接口是现有静态引脚规划，不代表 USB、OCTOSPI 或 Bootloader 已运行。硬件仍按[最小系统规划](../H7MS/最小系统与外围规划.md)实施。

## 一次更新应如何完成

1. **识别与下载**：查询板型、硬件版本、Bootloader 版本、当前镜像及协议版本。上位机取得适用的完整签名包，MCU 限制长度、目标区域和包格式。
2. **暂存**：以有限块大小写候选区，记录已持久化的有效进度。断线后依据 MCU 的状态继续，不能只信上位机缓存的进度；NOR 擦写恢复必须处理半写页/半擦扇区。
3. **预检查**：读回镜像并检查长度、哈希、签名和兼容性。只有完整合法候选、已知可用恢复镜像及维护条件都满足，才允许进入破坏性安装。
4. **停机**：停止接受运动目标，清除执行队列，使能关闭、CAN 待机、UART 方向回到接收、PWM 关闭，确认底板执行器处于允许维护的状态。进入 Bootloader 前明确写入有效的待更新状态。
5. **安装**：Bootloader 再验包，按可恢复的扇区事务安装。重启后从持久状态续做、恢复旧镜像或进入维护，禁止跳入半写应用。
6. **试启动**：新固件保持输出禁止，完成供电配置、存储、关键任务、通信和看门狗自检；具体健康条件按装配配置定义，不能以“程序跑到了 main”确认。
7. **确认/回退**：自检通过后提交确认，上报结果；未确认而复位/看门狗超时则恢复旧镜像。健康确认完成后仍须收到新的有效使能命令，不能自动恢复之前的电机目标。

这是本项目要求的状态语义。选用框架后须映射到其真实镜像槽位和状态格式，不能同时叠加两个互相矛盾的 Boot 状态机。MCUboot 的测试启动/确认/回退概念见[官方设计](https://docs.mcuboot.com/design.html)。

## Direct SMPS、Flash 与实时任务

Bootloader 从复位开始就必须使用本板的 Direct SMPS 启动配置，在供电/VOS 就绪后配置时钟及外存。应用与 Bootloader 共用供电契约；不能让新应用按 H723/H743 的 LDO 模板再次设置。供电模式的复位/锁定行为应沿用已归档的[最小系统恢复说明](../H7MS/最小系统与外围规划.md)，并在首次移植时测试冷启动、软复位和看门狗复位。

当前方案保留了现场复位/调试接口，但没有确认上位机能够独立切断并恢复 MCU 电源。因此，对于必须经过冷断电才能解除的供电配置问题，本阶段不能承诺远程自动救援；若整机要求无人值守处理这种故障，需在底板阶段评估由上位机独立控制的 MCU 供电开关，并验证不会同时切断救援端自身电源。

后台下载只写外部 NOR，仍会占用总线、DMA、CPU 和 Flash 写入时间，必须可限速、暂停。若 NOR 同时放日志/参数，采用明确的空间隔离与互斥，不能在擦写期间继续依赖同一芯片的任意 XIP 读取。

内部 Flash 擦写时，不依赖 cache 碰巧命中来保证服务。若要求此时继续喂看门狗或处理维护通信，需将有关例程、调用链、常量和必要向量放到可用 RAM/ITCM，并检查 DMA 可访问性和缓存一致性；也可设计分段擦写、上位机等待的停机协议。是否必须搬哪些代码由实际驱动与时序决定，不要求整个应用装入 RAM。

## 完整性、真实性与恢复边界

| 项目 | 首版设计要求 |
| --- | --- |
| 传输误码 | 帧 CRC/块校验、序号、偏移、长度、重传；只作传输检查 |
| 固件真实性 | MCU 端公钥验签；建议先评估 SHA-256 + ECDSA P-256，具体库、代码大小和耗时待测 |
| 签名范围 | 覆盖镜像内容及影响安装决策的板型、版本、长度、入口/目标、依赖等元数据，禁止可篡改的外置 manifest 控制安装 |
| 密钥 | 私钥不放在上位机镜像或 MCU 固件中；设备端保留受保护的可信公钥/密钥标识，轮换流程后续定义 |
| 状态持久化 | 双副本/日志提交、序号与校验，禁止只用一个随意覆盖的布尔标志；32 B 编程单位不等于掉电原子操作 |
| Boot 保护 | 评估扇区写保护及写入范围校验；研发保留 SWD 恢复，不在本阶段设置不可逆保护选项 |
| 版本策略 | 区分“故障回退”和“防安全降级”；安全版本计数需可信存储，外部 NOR 的可改计数不是硬件防回滚 |
| 确认顺序 | 新版确认前保留可用旧版及其参数；不要过早提升安全版本门槛而封死恢复路径 |
| 参数兼容 | 镜像回退不等于参数回退；参数 schema 升级须有旧版可读副本/可恢复迁移 |
| 整机兼容 | 包含上位机/下位机协议兼容范围；先更新哪一端由兼容矩阵决定，避免两端同时升级后互不认识 |

H735 的加密外设不能代替完整的可信启动设计，也不能把其他 STM32 系列的 TrustZone、STiRoT 或安全计数机制直接套用。本方案首先解决可验证交付和故障恢复；抵抗物理攻击的能力须在确定生产保护策略后单独评估。

若外部 NOR 硬件损坏且内部应用也无效，自动回退可能无法完成；应停在输出禁止的 Boot 维护模式，允许重新接收合法镜像，最终仍保留 SWD 现场恢复。OTA 的目标是让软件中断可恢复，不是声称能覆盖所有硬件损坏。
