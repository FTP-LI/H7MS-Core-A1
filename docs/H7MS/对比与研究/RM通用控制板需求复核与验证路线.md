# RM通用控制板需求复核与验证路线

2026-10-13。对象：H7MS-Core-A1，以及用户已有的 STM32H723VGH6／FreeRTOS 电控代码。代码型号由用户确认，应用源码尚未提供。本报告是选型评审，现有 H735 引脚、电源和板间接口基线保持原状。

后续决策：用户已确认继续使用 H735，并研究同底板及跨部位的多 MCU 协作，见[H735 多 MCU 协作与验证方案](../共性研究/H735多MCU协作与验证方案.md)。下文四路原生 CAN 的替代型号保留为条件性历史评审，不替代这一决定。

**建议用现有 H723 工程建立验证基准；若最终坚持单颗 MCU 原生四 CAN，优先验证 HPM6750IVM2，首阶段仅用一个内核。**它满足频率、CAN 数量和球距要求，片上 RAM 及 SD 卡资源也更贴近当前工程。代价是迁移到 RISC-V、重写底层驱动，以及更大的封装。HPM6E50IGN1 是偏小型化的备选；HPM5E31IVK 暂列紧凑候选，需要先补齐精确封装的引脚并发和开发板验证依据。

本次尚未找到可证明同时具备“四路独立 CAN 物理接口、至少 480 MHz、符合球距条件、现成 RM／FreeRTOS 应用”的即用成品板。芯片合格、评估板可开发、整机可参赛是三个不同结论。已有 H723 代码使继续 STM32 的成本最低，但 H723/H735 的三路原生 CAN 无法满足四路方案。[ST H723](https://www.st.com/en/microcontrollers-microprocessors/stm32h723vg.html)、[ST H735](https://www.st.com/en/microcontrollers-microprocessors/stm32h735vg.html)

## 本轮需求矩阵

| 需求 | 来源与优先级 | 选型或验收条件 |
| --- | --- | --- |
| RM 通用控制板 | 用户明确 | 共用底层和设备驱动，应用层支持不同机器人；不把某一种机器人的全部接口固定为必需 |
| 主频至少 480 MHz | 用户明确下限 | 在数据手册规定的电压、温度和存储配置下工作；不同内核不能直接按 MHz 比较实际性能 |
| 优先原生四 CAN | 用户反复表达的强偏好 | 本轮完整匹配候选按单 MCU 至少四个独立控制器筛选；三个控制器加多个插座、SPI 扩展或双 MCU 不计入原生四路 |
| BGA 球距至少 0.8 mm | 用户明确下限 | 按精确料号核查；不再推荐 0.5/0.65 mm 版本。球距相同不代表 PCB 层数、成本或返修难度相同 |
| 已有 H723VGH6／FreeRTOS | 用户确认 | 优先复用现有应用与调试流程；新平台必须证明移植成本可控 |
| IMU 与本地闭环 | 工程已有采样；RM 通用定位需要补强 | BMI088 SPI、独立片选/中断、时间戳、本地姿态和控制环；视觉/规划可在 Linux，关键控制不能依赖非确定性的上位机往返 |
| 接收机、裁判系统、板间通信 | RM 通用板应补齐的应用接口 | 分配专用 UART、DMA 与缓存；DBUS/SBUS 的电平、反相和帧格式分别确认，不把所有设备串口都固定为 RS-485 |
| 既有扩展资源 | 当前工程保留项，未获准删除 | 四组设备 UART+方向、上位 UART、辅助 UART、USB Device、SPI/I²C、4 PWM、ADC、状态指示及调试恢复接口 |
| 存储 | 当前工程保留项 | H735 1 MiB Flash、560 KiB 非备份 RAM 加 4 KiB 备份 RAM；W25Q128 是 16 MiB NOR，不是运行 RAM；四位 SDMMC TF 需单独保留或明确改为 SPI |
| 供电与故障行为 | 当前工程基线 | 核心输入 4.75～5.25 V；1.5 A 是设计预算，不是已测额定值。底板承担宽压与执行器功率；上电默认禁止、断联、看门狗、bus-off 和恢复流程需验证 |
| OTA、模型推理、以太网及双核 | 暂非首个闭环的必要条件 | 放到基础电机、IMU、接收机、裁判系统和故障行为验证之后，避免扩大首版范围 |

当前 USB 虽使用名为 USB_OTG_HS 的外设，规划是内置 FS PHY 的 **12 Mbit/s Device**，不能按 480 Mbit/s 计算现有上位链路。前三路 PWM 共用 TIM2 时也不能当作三个任意独立频率输出。这类并发条件比单纯数外设更影响“通用板”能否落地。

四条总线首先提供带宽分区、故障分区和扩展余量；未设计重复设备、备用线束和切换机制时，不能称为容错冗余。CAN FD 控制器接经典 CAN 电机时仍按该设备的经典 CAN 协议工作。

## H723代码迁移的实际边界

| 软件部分 | H723 到 H735 | H723 到 HPM |
| --- | --- | --- |
| 纯 C/C++ PID、运动学、状态机、协议打包 | 通常可以复用，仍需回归 | 通常可以复用；检查字节布局、浮点、原子操作和编译器行为 |
| FreeRTOS 任务、队列、应用调度 | 沿用框架，重核时钟和中断优先级 | API 层可保留；使用 HPM 的 RISC-V port，重核中断上下文、临界区、tick、栈及 FPU 保存 |
| HAL FDCAN、UART、SPI、DMA、USB | 多数沿用 STM32H7 框架，但引脚、DMA和实例配置需改 | BSP 重写；电机协议字节可能复用，发送排队、过滤器、中断、超时及错误恢复重新实现 |
| CMSIS-DSP、DWT、ARM汇编、MPU/Cache | 通常可沿用机制并重新验证 | ARM 专属部分替换；HPM DSP 库或可移植 C 算法需做数值与耗时对比 |
| 启动、链接、Flash、Bootloader | 核对芯片与电源启动差异 | 重建工具链、启动/链接、外部 Flash 启动与恢复；现有 OTA 分区不能照搬 |
| 调试工具 | 延续 STM32 的 SWD 工作流 | 配置 RISC-V JTAG、OpenOCD/FT2232 或受支持的 J-Link；现有 ST-Link/SWD 流程不能直接照搬 |

HPM 有[官方 FreeRTOS 示例](https://github.com/hpmicro/hpm_sdk/tree/main/samples/rtos/freertos/freertos_hello)和[工具链入门](https://hpm-sdk.readthedocs.io/en/latest/get_started.html)，因此无需从零移植 RTOS 内核；但它们不是 RM 电控 BSP。[FreeRTOS 官方 RISC-V 说明](https://compatibility.freertos.org/Using-FreeRTOS-on-RISC-V)也区分了芯片相关的中断扩展。

STM32 侧已有[Meta-Team 的 H723／DM-MC02／FreeRTOS RM 工程](https://github.com/Meta-Team/Meta-Embedded-NG/blob/main/README.md)，包含电机、BMI088、裁判系统、遥控及本地姿态任务，可作为迁移范围的实例；它是队伍维护的参考工程，不代表用户现有代码相同或本轮已经编译通过。当前未拿到用户源码，不能给出“只需几天”或具体代码复用百分比。

H723VGH6 与 H735VGH6 同封装也不能直接换焊：工程已经使用 H735 Direct SMPS 接法，需要重新核对电源球、启动配置及复用引脚。既有[两型号比较](H735VGH6与H723VGH6最终候选对比.md)保留这一约束。

## 先验证什么再定最终主控

1. **建立 H723 基准。**取得现有固件的可复现构建、map、任务清单、CAN ID/帧长/反馈频率及 DMA 缓冲分配；记录当前实际主频，不能把芯片 550 MHz 上限当成工程已运行频率。
2. **定义代表性 RM 负载。**用实际计划的电机/驱动器，覆盖底盘、云台/发射、板间或扩展设备的报文组合；测总线占用、反馈新鲜度、接收丢帧和发送排队。控制板自身无需重复承担智能驱动器内部 FOC，除非明确新增功率级。
3. **HPM 最小闭环。**单核 FreeRTOS、独立时间基准、一路真实 CAN 电机、BMI088 SPI/DMA、一路接收机及 USB/UART 日志；先保留可移植算法，再替换 BSP。测试包含 CAN 收发器和实际线束，内部 loopback 不能代替总线验证。
4. **四总线并发。**四路控制器同时连接物理接口，注入不同 ID/频率流量；并发运行 IMU、裁判 UART 和日志，保存 P99/最大周期、栈水位、队列峰值和错误计数。验证一条总线 bus-off 时其他总线不被软件阻塞。
5. **故障与回归。**断上位机、断接收机、总线拥塞、IMU失效、掉电/重启、驱动器离线和恢复；检查旧命令清除、重新使能、看门狗和硬件默认状态。通过后才冻结目标封装全部引脚、电源和 PCB。

建议第一轮用 **1 kHz 本地控制/姿态任务**作对比工况，并以“规定混合负载下无观测到的截止期丢失、CPU 和关键内存各预留约 30%”作为初始评审目标；这些是待确认的项目测试目标，不是 RM 官方门槛或当前已达到性能。报文频率应按实际驱动器能力确定，不能统一强设 1 kHz。

例如，假设某条 1 Mbit/s 经典 CAN 每毫秒承载 4 帧反馈和 1 帧指令，每帧按含开销的约 130 bit 估算，则占用约 65%。这只是带宽算例，实际要计 ID 类型、位填充、仲裁及重传。它说明第四条总线可能比更高 CPU 主频更有价值，但需要真实帧表证明。[TI CAN 基础](https://www.ti.com/lit/sloa101)

剩余需求输入为电机数量/协议、控制频率、板尺寸与成本上限、最终参赛年度及类别。上述信息影响最终引脚和验收；不影响先将 HPM6750IVM2 作为原生四 CAN 的首个验证候选。

## RM规则与最终决策

“适合 RM”还需要整机电源、接收机、裁判系统、功率限制及故障行为满足对应年度和机器人类别的规则，不能由 MCU 型号单独保证。本次检索的官方制作规范入口已列出 **2026 V2.0.0，2026-06-26**；后续赛季应重新按实际规则逐条核对，本报告未作整机合规签核。[官方机器人制作规范入口](https://bbs.robomaster.com/wiki/20204847/809871?source=7)

**当前可执行的选择：保留 H723／H735 作为低迁移成本基准，原生四 CAN 路线先评估 HPM6750IVM2＋HPM6750EVK2。**小型化优先时比较 HPM6E50IGN1，但要接受 TF 接口重新设计并验证；9 mm 的 HPM5E31IVK 需先完成目标封装与开发板资料闭环。三 CAN 若最终已够用，继续 STM32 的投入产出更好；这属于需求取舍，不能将它记作已经满足原生四 CAN。
