# 机器人上下位机主控架构与资源调研

调研日期：2026-09-15。对象：独立的H7MS-Core-A1通用机器人控制平台，考虑移动机器人、机械臂、传感采集和自动化台架。本文讨论工程设计与研发验收；不把一套接口清单等同于工业功能安全认证。

本文区分三种信息：**官方资料事实**附原始来源，**项目现状**来自仓库文档，**设计建议/算例**是针对本项目的推导。平台需要声明支持的接口、协议与负载范围；每个验证配置再确定节点数、频率、停止时间和环境。不存在适用于所有机器人的固定资源配方。用户确定的通用方向及据此提出的工程要求见[通用控制平台需求基线](10_通用控制平台需求基线.md)。

## 1. 先理解四个角色和两种“上下”

**上位机/下位机描述任务分工，核心板/底板描述电路分工。两者没有一一对应关系。**

| 角色 | 负责什么 | 本项目对应 |
| --- | --- | --- |
| 开发/训练计算机 | 仿真、训练、调试、数据分析与发布 | 外部开发计算机，型号不约束控制板 |
| 机载上位机 | 感知、地图/规划、任务管理、较大模型、用户交互 | PC、ARM或x86计算平台，通过协议/SDK接入 |
| 实时下位机 | 带时间戳的状态采集、周期调度、目标限幅、执行器通信、异常处理 | H7MS-Core-A1；可选执行小型Actor推理 |
| 关节/电机驱动器 | 本地位置/速度/电流环、编码器、功率级与电机保护 | 智能舵机内部控制器或独立FOC驱动板 |

```text
开发笔记本 ── 模型/固件/调试 ──> 机载系统

摄像头、激光雷达 ──> 上位机（PC/ARM/x86）
                         │ 目标、有效期、模式
                         │ 状态、时间戳、故障
                         ↕ USB / UART（当前候选链路）
机体IMU ──────────> 下位机（H7MS-Core-A1）
                         ↕ 逻辑信号，经核心板/底板连接器
                    应用底板（电源、收发器、急停、接插件）
                         ↕ 执行器总线
                    智能舵机 / 关节驱动器 ──> 电机

电池 ──> 保护与配电 ──> 执行器功率支路
                  └──> 逻辑电源；上位机和核心板分别核算负载
急停 ────────────────> 独立于普通任务软件的执行器禁止路径
```

H7MS的核心板和应用底板共同构成实时下位机的硬件系统；底板不是Linux上位机。计算模块与H7可以采用不同物理集成形式，但通用平台协议不绑定模块型号；当前A1不以自研Linux上位机为前提。

把高层计算与周期控制分开是公开平台中常见的架构。例如PX4把视觉等计算放在伴随计算机，通过串口或IP链路与飞控交互。[PX4系统架构](https://docs.px4.io/main/en/concept/px4_systems_architecture)

分板不是唯一实现方式。具备经过验证的实时环境、驱动和独立保护时，Linux计算平台也可以承担实时控制；是否增加MCU应由时序、故障边界和维护成本决定。实时性取决于整个执行链是否按期限完成，不能由“用了MCU/RTOS/ROS 2”直接推出。[ROS 2实时系统设计背景](https://design.ros2.org/articles/realtime_background.html)

## 3. 合格与否应检查能力，而不是只数接口

下面是面向本项目的工程要求分类，属于研究建议，不是厂家或行业统一认证条款。

- **基础必要**：缺失就无法形成可靠的控制平台；实现位置可以不同。
- **场景必要**：仅当选定机器人、传感器或执行器需要时才必须具备。
- **增强可选**：有明确收益后加入，不应先占满引脚再寻找需求。

### 3.1 上位机需要的资源与要求

| 编号/类别 | 能力 | 应明确的要求 |
| --- | --- | --- |
| U01 基础必要 | 计算与内存 | 目标软件栈能运行；测量CPU/GPU利用率、内存峰值和关键任务延迟，不能只比较核数/TOPS |
| U02 基础必要 | 系统存储与恢复 | OS、程序、模型、日志容量与写入寿命；异常断电后的启动和数据恢复方法 |
| U03 基础必要 | 下位机连接 | 至少一条满足吞吐和时延的链路；有版本协商、身份识别、重连和旧命令清理 |
| U04 基础必要 | 电源与散热 | 上位机及摄像头/USB外设分别核算峰值；验证欠压、启动浪涌、持续负载和热降频 |
| U05 基础必要 | 运维与故障报告 | 可查看日志、更新/回退程序、识别下位机离线；上位机重启不应自动恢复运动 |
| U06 场景必要 | 摄像头/雷达接口 | 按实际设备选择USB、CSI、Ethernet等，验证驱动和传输能力 |
| U07 场景必要 | 远程网络 | 按遥控/运维场景选择Ethernet/Wi-Fi；若可远程控制，需要认证与权限边界 |
| U08 增强可选 | GPU/NPU/高速扩展 | 大视觉模型、点云或其他负载提出需求后再评估，首版不把它们当作前提 |

这些能力可以由现有SBC和载板实现，不要求A1同时自研上位机。计算模块的外围设计应参考对应型号资料；不能把不同代CM模块的供电要求混用。[Raspberry Pi计算模块与载板文档](https://www.raspberrypi.com/documentation/computers/compute-module.html)

**H7MS建议：先用PC参考客户端验证控制板协议与SDK。**应用上位机另按软件、摄像头、模型、峰值负载和热设计选择；PC、ARM或x86只要满足协议与时序要求均可接入。当前没有依据将固定GB内存、GPU或特定计算模块列为控制板前置条件。

### 3.2 实时下位机需要的资源与要求

| 编号/类别 | 能力 | 对硬件与软件的要求 |
| --- | --- | --- |
| L01 基础必要 | 可启动、可恢复的最小系统 | 完整供电/去耦、时钟、复位、启动配置、下载调试通道；应用损坏后有恢复路径 |
| L02 基础必要 | 有界周期执行 | 定时器/单调时钟、中断优先级、可预测调度；记录周期抖动和超时，后台日志不得无限阻塞控制 |
| L03 基础必要 | 可用内存 | 固件、栈、状态、通信缓冲和算法工作区均有预算；核对DMA可访问区域与Cache一致性 |
| L04 基础必要 | 上位机协议 | 帧边界、长度/范围校验、校验码、序号、有效期、版本、身份与命令来源仲裁 |
| L05 基础必要 | 执行器接入 | 声明支持的设备接口与协议；按验证配置确认反馈字段、刷新率、超时和错误状态 |
| L06 基础必要 | 异常处理 | 上电默认禁止运动；任务/通信看门狗、欠压/故障处理、明确的停止策略与人工重新使能条件 |
| L07 基础必要 | 可观测与可维护 | SWD/下载、复位原因、故障码、软件/硬件版本、测试点和最小诊断日志 |
| L08 场景必要 | 机体状态感知 | 足式平衡通常需要IMU；轮式编码器/里程计、机械臂编码器和限位按任务配置 |
| L09 场景必要 | 模拟量与离散量 | 根据供电监测、温度、触地、急停和故障输入确定ADC/GPIO数量，明确默认电平与断线行为 |
| L10 场景必要 | 多总线与同步 | 按节点数量、报文量、线束分区和故障隔离需求确定UART/CAN数量，定义采样及动作时序 |
| L11 增强可选 | 本地大容量存储与推理 | QSPI、TF及RL推理要有明确容量/时延需求；基本控制应有不依赖TF的路径 |
| L12 增强可选 | 加热、冗余与扩展 | IMU恒温、多IMU、双控制器、额外PWM/编码器、RGB等按收益取舍 |

最小系统电源、封装、时钟、复位、启动和调试的设计依据可直接从[ST AN4938](https://www.st.com/resource/en/application_note/an4938-getting-started-with-stm32h74xig-and-stm32h75xig-mcu-hardware-development-stmicroelectronics.pdf)逐项落实。实时路径为何要避免不可预测的阻塞和分配，见[ROS 2实时系统设计](https://design.ros2.org/articles/realtime_background.html)。其原则可参考，不能把Linux示例中的数值直接作为H7验收值。

“有看门狗”还需确认喂狗条件：如果只有一个定时中断持续喂狗，即使业务任务已卡死，也可能无法检测故障。建议在关键任务的进度和数据有效性均通过后才允许喂狗；通信超时与CPU卡死需要分别测试。

### 3.3 底板与驱动器需要的资源

| 所在位置 | 基础或场景要求 | H7MS归属建议 |
| --- | --- | --- |
| 底板配电 | 电池输入、保险/过流、反接/浪涌、逻辑降压、连接器载流能力 | 结合电池和实际电流选型；执行器大电流不经过核心板 |
| 总线物理层 | UART对应TTL/RS-485等转换，CAN收发器、终端、ESD与线束接口 | 随电气场景变化的部分放底板，明确逻辑域和外部线电压 |
| 硬件禁止路径 | 急停/故障能够禁止执行器，不依赖Linux或普通周期任务正常运行 | 核心板报告状态；底板/驱动端实现实际禁止输出或功率切断 |
| 关节驱动器 | 编码器、局部控制环、电流采样、功率级、过温/过流与失联处理 | 智能舵机内置或独立驱动板本地完成 |
| 可回馈负载 | 制动时能量回流、母线过压和电源吸收能力 | 由配电/驱动系统设计，不交给H7的3.3V逻辑电源处理 |

CAN控制器的TX/RX逻辑不能直接连接CANH/CANL，必须经过合适的收发器。[TI CAN物理层说明](https://www.ti.com/document-viewer/lit/html/SSZTCN3) 高速CAN常见线型网络在两端配置终端，分支和拓扑需要具体核查，不能每个节点随意都接终端。[TI可选终端参考设计](https://www.ti.com/tool/TIDA-01238)

驱动器实现本地级联环的例子见[ODrive控制器](https://docs.odriverobotics.com/v/latest/manual/control.html)。制动能量和母线电压处理见[ODrive硬件配置](https://docs.odriverobotics.com/v/latest/manual/hardware-config.html)；具体能力随驱动产品变化，不能把其中某个型号的制动电阻功能泛化到全部舵机。

## 4. 接口应该如何选择

| 接口 | 适用位置 | 必须弄清的问题 |
| --- | --- | --- |
| USB | 上位机与下位机、调试/升级 | 谁是Host/Device、连接器固定、重连、供电回灌、端到端延迟；USB-C只描述连接器形态 |
| 逻辑UART | 短距离板间连接或连接物理层器件 | 逻辑电压、波特率、流控/缓存、线束长度与地参考；不能直接当成RS-232或RS-485 |
| RS-485/半双工执行器总线 | 分布式舵机、较长线束 | 方向切换、节点ID、收发等待、终端/偏置按物理层要求配置；“半双工”本身不指定电压标准 |
| CAN/CAN-FD | 智能驱动器或传感节点 | 节点协议、标称/数据速率、收发器、电气拓扑、终端、bus-off恢复；支持CAN-FD的MCU不代表执行器支持FD帧 |
| Ethernet | 需要更高吞吐的上位链路或网络化驱动 | 普通以太网与EtherCAT等实时工业协议需要不同的完整实现，MAC存在不等于接口已完成 |
| SPI/I²C | 板上或短距离传感器/扩展 | SPI片选与DMA分配；I²C地址、上拉、电容和总线卡死恢复，不能无条件拉遍整台机器人 |
| PWM/编码器/ADC | 直接驱动接口或专用测量 | 所有权在哪一层、同步采样、分辨率与电平；使用智能驱动器时未必需要在核心板重复引出 |

这些取舍是本项目建议。物理层、帧协议和设备控制模式必须同时匹配。ROBOTIS的DYNAMIXEL协议提供半双工和批量读写的具体例子，它是具体厂商协议示例，不能据此宣称所有半双工设备兼容。通用平台通过适配器接入明确版本的设备协议。[DYNAMIXEL Protocol 2.0](https://docs.robotis.com/docs/dxl/protocol/protocol2/)

## 5. 用四笔预算替代“接口越多越好”

### 5.1 先算端到端时间

```text
状态采样 → 等待/排队 → 传输 → 状态处理/推理 → 命令传输 → 驱动器应用目标
```

不仅记录推理耗时，还要记录观测的年龄、关节反馈之间的时间差、排队时间和命令实际生效延迟。接收时间戳不等于采样时间戳；上、下位机时钟未同步时不能直接相减，需要同步策略或在同一时钟域测量。

| 项目 | 仓库当前初始目标 | 本次解释 |
| --- | --- | --- |
| IMU采样 | 1 kHz | 本项目候选值，需结合IMU输出速率和滤波延迟 |
| 状态估计 | 500 Hz | 可以与采样不同频率，须定义输入新鲜度 |
| 可选推理基准 | 200 Hz，5 ms周期 | 推理最坏耗时目标≤2 ms，整个控制周期目标≤4 ms |
| 设备通信 | 100～250 Hz算例 | 尚未经过代表设备与混合负载验证，按配置冻结 |
| 软件安全检查任务 | 1 kHz | 只是软件采样频率，不代表急停系统总响应为1 ms |

这些目标来自[固件架构](02_固件架构.md)和[RL部署](05_RL策略部署.md)，不是统一行业门槛。软件环周期和机器人闭环有效带宽也不是同一个量。台架测得的最大值只是该测试条件下的观测最大值，不能直接宣称已证明所有情况下的最坏执行时间。

### 5.2 再算带宽：上位链路与执行器链路分开

以下都是**假设算例**，不是实测抓包，也不是已确定的平台协议格式。字节数含假设帧开销，但未含额外等待/重传。

对于8N1 UART，每字节占10个线路位：

```text
线路位率需求 = 每帧字节数 × 每秒帧数 × 10
```

假设上位机每次发送80字节目标，下位机返回200字节状态，均为200 Hz：

| 方向 | 线路需求 | 921600 baud下理论占用 |
| --- | ---: | ---: |
| 上位→下位 | 160,000 bit/s | 17.4% |
| 下位→上位 | 400,000 bit/s | 43.4% |

115200 baud对这两路假设负载均不足。全双工UART按每方向分别检查；共享半双工链路才要将两方向时间相加。921600只是算例，不代表现有上位机和布线已经支持；还需考虑突发、缓存、调度、时钟误差和链路测试。

再假设12个执行器共用1 Mbaud半双工总线，每个执行器每周期发送14字节、返回18字节：

```text
每周期字节数 = 12 × (14+18) = 384字节
纯传输时间   = 384 × 10 / 1,000,000 = 3.84 ms
200 Hz周期内占用 = 3.84 / 5 = 76.8%
```

这还未计方向切换、设备处理、帧间隙、错误和重试。如果有四条真正独立、并行工作的总线且每条只带3个节点，理想纯传输时间才可降到每条0.96 ms。现有线束能否拆分、MCU与软件能否并发必须另证，不能只凭“四组TX/RX”得出结论。实际协议支持时，批量读写可降低开销。[DYNAMIXEL批量读写示例](https://docs.robotis.com/docs/dxl/protocol/protocol2/)

CAN不能套用UART的10位/字节公式，还需计算帧头、仲裁、位填充、帧间隔、重传以及FD的数据阶段速率。[TI CAN基础](https://www.ti.com/lit/sloa101)

### 5.3 计算与内存预算

1. Flash：Boot、主程序、库、内部权重、参数和恢复/升级布局。
2. RAM：静态数据、各任务栈峰值、算法激活/工作区、收发队列、日志缓冲和对齐开销。
3. 算力：估计、通信、控制和推理的并发占用、抢占与截止时间。
4. 内存位置：容量够用之外，还需确认每个DMA控制器能访问哪些区域。

当前H743VI为480 MHz、2 MB Flash、约1 MB RAM的基线。[ST H743VI](https://www.st.com/en/microcontrollers-microprocessors/stm32h743vi.html) 可选MLP算例的23,948个参数按FP32计95,792字节，但权重可以从Flash读取，不能把权重大小直接当成RAM需求。详细算法和选型讨论见[主控选型与资源预算](07_主控选型与资源预算.md)。

需要修正一种过度简化的说法：对H743，普通外设DMA1/DMA2不能直接使用DTCM作为缓冲，但MDMA可以访问TCM。因此必须写明是哪一种DMA，不能统称“所有DMA都不能访问DTCM”。Cacheable共享缓冲还要按实际传输方向处理一致性。[ST NUCLEO-H743ZI ADC/DMA示例说明](https://github.com/STMicroelectronics/STM32CubeH7/blob/master/Projects/NUCLEO-H743ZI/Examples/ADC/ADC_DMA_Transfer/readme.txt)、[ST AN4839缓存说明](https://www.st.com/resource/en/application_note/an4839-level-1-cache-on-stm32f7-series-and-stm32h7-series-stmicroelectronics.pdf)

### 5.4 电源、热与机械预算

- 分别列电池/执行器、上位机、核心板、传感器和外设的电压、持续/峰值电流、启动顺序与掉电状态。
- 核心板现有BASE_5V≤1.5 A是待验证设计目标，相当于输入侧7.5 W上限量级；不是外部上位机和全系统都能从这里取电的承诺。
- GPIO输出能力、辅助3.3V、电源转换器能力与连接器载流能力是不同约束；并联触点数不能简单乘成可用电流。
- 电机启动、堵转、制动与逻辑电源恢复应有测试条件；USB/底板双电源要检查反灌，USB供电不能默认带满加热等负载。
- 规定板尺寸、层叠、安装孔、锁止/应力释放、振动、线束固定、温度范围和测试点可达性，尤其关注IMU与热源/振动的耦合。

该列表为设计建议，数值来自当前[硬件设计](01_硬件设计.md)，最终需器件与台架验证。电机再生制动的能量可能抬高直流母线，不能仅检查静态电压。[ODrive电源与制动配置](https://docs.odriverobotics.com/v/latest/manual/hardware-config.html)

## 6. 软件协议和安全行为也是主控板要求

### 6.1 一个动作必须具备上下文

建议命令至少关联：协议版本、发送者/控制模式、序号、有效期、设备映射与单位、目标值及完整性校验。状态至少包含本地时间戳、数据有效性、设备能力/测量、电源/故障信息及当前使能状态；关节和IMU是具体设备类型。

必须定义：旧命令是否丢弃、重复帧如何处理、缓冲满时保留什么、上位机和本地策略谁拥有控制权。CRC用于发现传输损坏，不能代替远程操作者认证；如开放网络控制或远程升级，还需相应授权与可信更新设计。

### 6.2 故障策略不能只有“复位一下”

| 故障 | 建议规定的动作 | 必须测量/确认 |
| --- | --- | --- |
| 上位机断联/重启 | 超时后执行已定义停止策略，拒绝过期动作，重连后重新使能 | 最后有效命令到策略触发的时间、重连是否出现突跳 |
| 下位机卡死/复位 | 由硬件默认状态、看门狗和驱动端失联机制抑制运动 | 不依靠卡死任务的软件分支，复位期间输出实际电平 |
| 传感器失效/陈旧 | 撤销依赖该观测的控制模式，进入可验证降级/停止流程 | 无效数据检测时间、是否沿用旧观测 |
| 执行器离线/总线异常 | 按配置的故障分组与应用要求处理离线设备和其余设备 | 不无限等待单个节点，恢复后不自动执行积压目标 |
| 过温/欠压/功率故障 | 按严重度限功率、停止或硬件禁止 | 故障阈值、迟滞和整个反应链的延迟 |
| 升级中断/参数损坏 | 保持禁止运动，可恢复到可用程序/参数 | 各中断阶段重启的实际结果 |

ODrive展示了驱动端通信看门狗的具体实现：收到相应控制命令时喂狗，通信中断后可禁止电机。[ODrive通信看门狗](https://docs.odriverobotics.com/v/latest/manual/can-protocol.html) 这是可参考机制，各适配器必须声明并验证实际设备的失联能力，不能默认所有设备一致。

对足式机器人，停止发命令、维持姿态、受控下蹲和切断力矩产生的机械后果不同。不能把“上位机掉线后一律立即断电”当成所有情况的默认答案；需要台架支持、机械保护与具体故障策略。既有A1的硬件急停/禁止路径仍需保留，不能只依赖软件受控停机。

## 7. 对照H7MS现有资源：哪些必要，哪些可以后置

下面是**开发优先级建议**。v0.7料号、引脚和J1/J2契约本次没有改变；如后续删减或重分配，需明确修订对应基线。

| 现有规划 | 本项目判断 | 建议处理 |
| --- | --- | --- |
| H743、供电、时钟、复位、SWD | 基础必要；型号仍需按需求验证 | 保留评估基线，先完成最小系统与恢复验证 |
| USB＋上位UART | 至少一条主链路必要，第二条利于维护 | 明确主链路和调试用途，不把两条都承诺为实时冗余链路 |
| SPI IMU | 对姿态控制为场景必要，通用串口/CAN模式不强制依赖 | 型号、轴向和采样特性需明确，配置声明哪些模式依赖它 |
| IMU加热＋NTC | 恒温是增强功能，温度有效性检查仍重要 | 先测温漂需求；在保留加热设计时关闭TIM8共用和过热保护问题 |
| 四路设备UART | 作为多设备/分区通信候选，需证明复用及并发可用 | 先单总线再扩展，声明节点/报文/频率范围，不以12维策略限定总数 |
| 双CAN-FD逻辑 | 作为通用平台CAN设备接入候选 | 验证底板落实物理层，与串口并列验证；分别声明经典CAN/FD协议与组合能力 |
| 32 MB QSPI | 模型包/回退/日志的容量扩展 | 当前小MLP不直接要求32 MB；依据升级布局与存储预算解释容量 |
| 四位SDMMC TF | 对长期离线采集有价值，基础控制不依赖它 | 首个闭环可先用上位机日志及最小故障记录；TF并发与掉卡测试后加入 |
| TIM1互补PWM、TIM2等 | 使用智能驱动器时属于实验扩展 | 不据此宣称核心板具备完整FOC；重新分配前先核对真正需要的控制接口 |
| I²C底板EEPROM、安全握手 | 多底板兼容时有价值 | EEPROM能力表不能替代电气防误插；测试错误底板和连接器松动 |
| RGB、蜂鸣器、额外片选 | 状态指示需要，具体器件和数量可选 | 简单状态灯可完成早期诊断，不让RGB占用干扰关键时序 |
| 电源监测、默认禁止、急停与故障链 | 基础必要 | 优先落实完整硬件路径、阈值和故障注入证据 |
| 双50Pin连接器 | 当前机械方案 | 不是机器人主控通用门槛；按真实信号/回流/电流和装配约束复核 |

当前主要缺口是通用能力范围及其证据：尚未确定代表设备/协议、节点与报文上限、资源复用矩阵、组合负载、数值化停止要求，也没有EDA和上板结果。先完成平台需求与代表配置，再依次验证单链路和多配置并发，避免靠增加接口数量定义通用性。

## 8. 通用验证系统与验收证据

### 8.1 首个闭环范围

PC参考客户端连接H7核心板与通用验证底板，先实现最小系统、可靠上位链路、设备接口、状态机和诊断。无动力模拟通过后，分别验证串口设备、CAN设备及传感/I/O配置，最后加入混合负载。具体机器人应用可独立开展；RL、恒温和扩展日志按能力单独验收。

这是通用研发路线草案，没有改动v0.7引脚或电气契约。不同配置应共用BSP、调度与安全服务；同协议节点通过配置增加，新协议通过适配器增加。单设备点亮、平台发布和整机应用验证分别记录，不能相互替代。

### 8.2 验收矩阵

| 验收项 | 必须保存的证据 | 通过依据 |
| --- | --- | --- |
| 最小系统/电源 | 电压、电流、启动/掉电和负载突变波形，精确BOM与配置 | 所有额定值和时序满足器件要求，未解释的复位/反灌问题关闭 |
| 上位协议/SDK | 参考客户端、版本/能力协商、链路负载与重连记录 | 上位接入可复现，满足通信期限；实际应用上位机负载另做系统验收 |
| 总线与节点 | 原始抓包、ID/线束表、逐方向带宽、错误与超时统计 | 达到所需反馈和控制频率，报文开销及异常负载有余量 |
| 时间与内存 | 固定条件下平均/P99/最大时延、数据年龄、链接map与栈峰值 | 声明的组合负载满足截止时间和各区域内存预算 |
| 通用性 | 串口、CAN、传感/I/O配置及混合运行记录，适配器与能力表 | 共用核心和平台服务，设备数量/模式可配置，资源冲突及不支持模式可拒绝 |
| 故障与重新使能 | 断联、复位、卡死、传感器异常、急停等故障注入记录 | 在事先定义的反应时间内进入规定状态，恢复后不意外运动 |
| 恢复与升级 | 固件/参数损坏、升级中断、TF拔出等结果 | 仍能进入可恢复且禁止运动的状态，非实时存储不拖死控制 |
| 机械与热 | 装配图、极性/针序复核、振动/温度/连接器测试记录 | 满足所声明使用环境，无松脱、过热和不可接受的测量误差 |
| 可复现发布 | EDA源文件、BOM、工具链、源码/模型哈希、固件与报告 | 另一台工作机能按说明重建并对应到被测版本 |

测试时长、温度范围、最大动作过期时间和停止反应时间目前未冻结，必须按拟发布的验证配置补齐。缺少阈值只能记为待验证，不能填写“通过”。200 Hz/2 ms/4 ms仅是可选推理算例的初始目标，不是每一种机器人的合格线。
